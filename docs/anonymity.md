# 익명성 · 중복 제출 방지 · 남용 방지: 설계와 한계

이 문서는 "완전한 익명"을 주장하지 않는다. **무엇을 막았고, 무엇은 못 막는지**를 구분해 기록한다.
보안 검토가 끝나기 전에는 운영 환경에서 `FEATURE_SURVEYS`, `FEATURE_SUGGESTIONS`를 기본값 `false`로 둔다.

## 1. 위협 모델 — 누구로부터 숨기는가

| 관찰자 | 목표 | 현재 수준 |
|---|---|---|
| 교수자·관리자 (앱 화면·API만 사용) | 누가 어떤 응답을 했는지 알 수 없어야 함 | **보장** (아래 2장, 테스트로 검증) |
| 다른 학생 | 타인의 응답·참여 여부를 알 수 없어야 함 | **보장** |
| DB에 직접 접근 가능한 운영자 (Supabase 대시보드, 백업 파일) | 응답과 계정의 연결 | **부분적으로만 방어** (3장 한계) |
| 호스팅 사업자 로그·네트워크 기록 | 요청 시각과 응답의 연결 | **부분적으로만 방어** |

## 2. 적용한 방어

1. **데이터 분리**: `survey_participations(survey_id, user_id)`는 "참여했다"는 사실만 저장한다. `survey_responses / survey_answers`에는 사용자 ID, 제출 시각, IP가 **없다**. 두 테이블을 잇는 외래키나 공통 값이 없다. (`test_anonymity_schema_has_no_link`)
2. **순차 ID 미사용**: 응답·답변·건의의 기본키는 UUIDv4. 자동 증가 번호로 제출 순서를 추정할 수 없다.
3. **화면·API 노출 차단**: 참여자 목록을 반환하는 API가 없다. 교수자 화면은 총 응답 수와 통계만 보여준다. 학생은 **자신의** 참여 여부만 본다. (`test_staff_cannot_see_who_participated`)
4. **소수 응답 보호**: 응답 수가 `min_results`(기본 5) 미만이면 집계·원문·엑셀을 모두 막는다. 응답이 2~3건이면 문체나 내용으로 작성자를 짐작할 수 있기 때문이다.
5. **결과 섞기**: 자유응답 원문은 문항마다 따로 무작위로 섞어 보여준다. 엑셀 응답 행 순서도 섞는다.
6. **로그 차단**: 익명 제출 요청(`POST /api/surveys/{id}/responses`, `POST /api/suggestions`)은 uvicorn 접근 로그에서 빠진다. 감사 로그에도 남기지 않는다. 검증 오류 응답에도 입력 원문을 돌려주지 않는다. (`test_no_submission_audit_or_log`, `test_access_log_filter_hides_anonymous_posts`)
7. **권한 부재**: 작성자를 역추적하는 권한이나 기능이 코드에 없다. (`test_no_deanonymization_permission_exists`)
8. **자체 암호 프로토콜 미사용**: 블라인드 서명 같은 직접 구현 암호는 쓰지 않았다. 검증되지 않은 암호 구현은 오히려 위험하다고 판단했다.

## 3. 남은 한계 (중요)

| # | 한계 | 왜 남는가 | 완화책 / 권고 |
|---|---|---|---|
| L1 | **DB 물리 저장 순서** | PostgreSQL은 행을 대체로 삽입 순서대로 저장한다. DB 관리자가 `ctid` 순서로 participations와 responses를 나란히 덤프하면 n번째끼리 맞춰볼 여지가 있다. | 운영 DB 접근자를 최소화한다(Supabase 멤버 = 관리자 1명). 응답이 쌓인 뒤 주기적으로 `VACUUM FULL`/`CLUSTER`로 재정렬하는 방안을 검토한다. 완전 해결에는 응답 배치 지연 저장 같은 설계 변경이 필요하다. |
| L2 | **WAL·백업·DB 통계** | 트랜잭션 로그와 PITR 백업에는 커밋 시각이 남는다. | 운영 DB 백업 열람 권한을 제한한다. |
| L3 | **호스팅 플랫폼 로그** | Render·프록시가 남기는 HTTP 로그(시각·IP·경로)는 앱이 통제할 수 없다. | 접근 로그에서 경로는 보여도 본문은 없다. 다만 "언제 누가 제출 API를 불렀는지"는 플랫폼 관리자가 알 수 있다. 이 한계를 학생 안내문에 명시하는 것을 권장한다. |
| L4 | **같은 트랜잭션 커밋** | 참여 기록과 응답은 한 트랜잭션에 저장된다(중복 방지 원자성 때문). 커밋 시각 자체는 DB 내부에서 같다. | 앱 테이블에는 시각을 저장하지 않는다. L2와 같은 범주다. |
| L5 | **응답 내용 자체** | 학생이 응답에 자기 이름이나 고유한 경험을 쓰면 익명성이 깨진다. | 응답 화면에 안내 문구를 표시하고, 외부 AI 전송 전 이메일·전화번호·학번을 마스킹한다. |
| L6 | **엑셀 행 단위** | 엑셀 '응답' 시트는 한 사람의 여러 답이 한 행에 묶인다(구글폼과 동일). 응답이 적으면 조합으로 식별 위험이 생긴다. | 최소 응답 수 미만이면 내보내기를 차단한다. |

**결론**: "교수자가 앱을 통해 작성자를 알아낼 수 없다"는 수준은 테스트로 검증했다. 다만 **DB와 인프라에 직접 접근할 수 있는 운영자**를 상대로 한 익명성은 보장하지 못한다. 학생 안내문에 이 범위를 정확히 적어야 한다.

## 4. 익명성과 중복 방지를 동시에 달성할 수 있는가

- 서버가 "이 계정은 이미 냈다"를 알아야 하므로 참여 사실은 반드시 저장된다.
- 이론적으로는 블라인드 서명이나 익명 자격증명으로 참여 사실과 응답을 암호학적으로 분리할 수 있다. 하지만 검증된 라이브러리, 키 관리, 별도 발급 서버가 필요해 이 규모의 수업 서비스에는 과하다. 자체 구현은 지시서에서도 금지했다.
- 그래서 **"앱 기능상 비연결 + 소수 응답 보호 + 운영 접근 최소화"**를 현실적인 목표로 삼았다.

## 5. 건의함 남용 방지와 익명성

- 제출 **횟수**는 무제한이고, **속도**만 제한한다(분당 5회, 시간당 30회).
- 속도 제한 키는 `HMAC(SECRET_KEY, user_id)`의 일부다. 서버 **메모리**에만 있고, 제출 시각 목록 외에는 아무것도 저장하지 않는다. 제출 내용과 함께 저장되지 않으며, 재시작하면 사라진다.
- 길이 제한(2000자), 제어문자 제거, 유형 화이트리스트를 적용한다. 화면은 `textContent`로만 렌더링해 HTML이나 스크립트가 실행되지 않는다(E2E로 확인).
- 한계: 메모리 기반이라 서버를 여러 대로 늘리면 인스턴스별로 따로 센다. Redis로 바꿀 경우에도 사용자와 내용을 함께 저장하지 않는 원칙을 유지해야 한다.
- 도입하지 않은 것: 계정별 제출 기록, IP 기록, 내용 해시 기반 중복 탐지(작성자 연결 위험).

## 건의 접수 알림 (2026-11-13 변경)

새 건의는 교수자 앱 알림함과 설정된 외부 알림으로 5~10분 무작위 지연 후 안내한다. 실제 표시·전송은 앱 열기, 기기 연결 및 발송 상태에 따라 더 늦을 수 있다. 건의 레코드는 여전히 작성자·IP·정확한 제출 시각을 저장하지 않는다. 알림은 내용·카테고리·건의 ID를 저장하지 않으며, 별도의 무작위 이벤트 키를 사용한다. 단, 예약된 알림 시각과 전송 운영 메타데이터로 제출 시간대를 추정할 수 있으므로 완전한 시간적 익명성을 보장하지 않는다. 학생 제출 화면에도 이 한계를 안내한다. 과거 건의에 대한 소급 알림은 생성하지 않는다.
